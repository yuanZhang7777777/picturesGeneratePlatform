# 独立批量出图平台完整设计

日期：2026-07-28  
状态：待用户复核；不是已完成实现或部署  
目标读者：产品负责人、实现工程师、测试与运维人员

## 1. 结论

建设一套完全自有的公司内部批量出图平台，替代飞书与 Coze 提交、编排和取图链路。

系统核心不是“一个文件夹等于一个商品”，而是：

```text
上传批次 batch
  └─ 商品集群 cluster
      ├─ 一张主参考图
      ├─ 0–15 张同商品补充角度图
      ├─ 商品事实与集群提示词
      └─ 一套输出槽位 generation
          └─ 每次重做形成新 attempt，旧版本永久保留
```

用户上传文件夹后，每张图片默认创建一个商品集群。用户把其他图片拖入该集群，表示它们是同一商品的不同角度；合并后的集群只生成一套图。

首版面向最多约 100 名内部员工，组织级每日最多接收 2,000 次生图提交尝试。系统本身按该规模设计；APIMart 账号的真实并发和限流未公开，正式承诺“当天全部完成”以前必须通过分阶段契约测试确认供应商吞吐。

## 2. 已冻结范围

### 2.1 首版包含

- 管理员创建、停用和重置内部员工账号。
- 管理员与运营两种角色。
- 运营只能访问本人批次、图片、Prompt 和结果；管理员可查看全部。
- Chrome/Edge 文件夹拖拽或文件夹选择上传。
- 每张图片默认一个商品集群。
- 拖拽合并、移出、调整主图和补充角度图。
- 全局提示词、集群提示词、商品事实和不得改变项。
- 多个 TXT 导入、作用域建议、人工确认和修改。
- AI 商品资料整理、Prompt 优化和一套图策划。
- Shopee/TikTok 平台规则配置和版本快照。
- 生成前付费任务预检与二次确认。
- APIMart 异步提交、状态查询、结果下载和 OSS 归档。
- 单张失败只重做该张，旧结果和旧 Prompt 保留。
- 批次、集群、单张和版本级实时状态。
- 结果预览、人工通过/不通过、单张下载和整批 ZIP。
- 组织与个人每日额度。
- 审计日志、运行指标、备份和恢复。

### 2.2 首版不包含

- 飞书、Coze 或旧工作流兼容层。
- 公开注册、短信验证码、第三方客户租户和在线收费。
- 通用工作流编辑器。
- 在线 PS、画布或像素级图片编辑。
- 竞品图片分析。
- 多模型自由切换。
- 自动无限重试。
- Webhook；首版使用 APIMart 任务查询。
- Redis、RabbitMQ、微服务或 Kubernetes。
- 普通运营编辑平台合规规则。
- 删除历史结果；首版只允许归档隐藏。

## 3. 用户、登录与权限

### 3.1 账号

- 不提供公开注册。
- 管理员在后台创建账号，录入姓名、工号/内部标识和初始临时密码。
- 首次登录必须修改密码。
- 密码至少 12 个字符；使用 Django 内置强密码哈希。
- 连续 5 次失败后，用户名与来源 IP 组合锁定 15 分钟。
- 登录会话有效期 12 小时；退出、停用账号或管理员强制注销后立即失效。
- 管理员重置密码时生成一次性临时密码，不通过日志或前端接口返回原密码。

### 3.2 角色

`operator`：

- 只能创建和查看自己的批次。
- 可整理集群、编辑资料、生成、重做、验收和下载自己的结果。
- 不能修改额度、用户、平台规则或系统参数。

`admin`：

- 查看全部批次和系统指标。
- 创建、停用和重置账号。
- 调整个人额度、暂停队列、处理 `submit_unknown`。
- 发布平台规则和输出模板。
- 不可直接修改已经提交任务的 Prompt/参考图快照。

### 3.3 对象级隔离

所有批次、资源、集群、Prompt 版本和生成记录都带 `owner_id` 或从所属批次推导所有者。每个查询和修改接口都在服务端按当前用户过滤，不能依赖前端隐藏。

下载图片不返回公开永久 URL。平台验证权限后生成短时 OSS 签名下载地址。

### 3.4 临时 IP 入口

服务器当前 `18081` 和 `18082` 已占用，`18083` 在 2026-07-28 的只读核查中空闲。

临时试用：

- 使用 `http://<服务器>:18083`。
- 阿里云安全组只放行已确认的公司出口 IP。
- 只使用临时测试账号和非敏感测试素材。
- 不允许把该入口视为正式生产登录入口。

正式员工上传真实商品素材前必须切换域名 HTTPS；届时启用 `Secure` Cookie、HSTS 和标准 443 入口。没有 HTTPS 时不扩大到 100 人。

## 4. 产品信息架构与实时交互

### 4.1 页面

1. 登录页。
2. 我的批次。
3. 新建批次与文件夹上传。
4. 商品集群工作台。
5. Prompt 与一套图策划。
6. 生成预检。
7. 任务进度与结果验收。
8. 管理后台。

### 4.2 我的批次

每行显示：

- 批次名、平台、站点和创建时间。
- 商品集群数、计划图片数。
- 已完成、处理中、失败和待补资料数量。
- 组织队列位置和更新时间。

筛选：草稿、排队中、生成中、部分完成、已完成、需处理、已归档。

### 4.3 上传

- 使用 `<input webkitdirectory multiple>` 和拖放区域保留相对路径。
- 浏览器先把文件清单发送给服务端，服务端返回逐文件、短时、精确对象键的 OSS 预签名上传地址。
- 浏览器直接上传 OSS，显示每个文件与整个批次的进度。
- 上传完成后服务端逐个执行 HEAD 校验，再进行实际格式验证。
- 页面刷新或断网后可继续未完成文件，不重复上传已验证对象。

首版限制：

- 图片：JPEG、PNG；单张不超过 20 MB。
- TXT：UTF-8，单个不超过 256 KB。
- 单批最多 100 张源图片、20 个 TXT。
- 单商品集群最多 16 张参考图。
- 单批预检后最多创建 300 个生图任务。
- 不支持 ZIP、PSD、PDF、视频、HEIC 或可执行文件。

原图保留不变；系统另建已校正 EXIF 方向的标准参考副本。服务端生成对象键，不使用用户文件名作为存储路径。

### 4.4 商品集群工作台

- 上传完成后每张有效图片创建一个独立商品集群。
- 图片卡片可拖入其他集群；被拖入后成为补充角度图。
- 集群必须保留一张主参考图。
- 支持从集群移出图片；移出后自动形成新的独立集群。
- 合并、拆分和切换主图只影响尚未确认的新版本，不修改已提交生成任务的历史快照。
- 同一商品集群超过 16 张时禁止生成并提示移除。
- 系统可建议疑似相同商品，但首版绝不自动合并。

并发编辑使用整数 `version`。保存时提交上次读取的版本；版本不一致返回冲突并要求刷新，避免两个标签页相互覆盖。

### 4.5 TXT 与提示词作用域

TXT 是提示词资料来源，不是任务主键。

- 根目录 TXT 默认建议为全局资料。
- 与图片同名的 TXT 默认建议分配给该图片初始集群。
- 其他 TXT 显示为“待分配资料”。
- 多个 TXT 不自动拼接；用户必须确认其作用于全局或一个/多个集群。
- 文件内容导入编辑器后保留来源文件名和原始文本快照。

最终输入分为：

1. 全局创意与品牌要求。
2. 商品名称和品类。
3. 已确认事实：卖点、规格、材质、包装内容、使用方法。
4. 商品身份硬约束：颜色、Logo、结构、部件数量、接口和连接关系。
5. 禁用内容、敏感声明和不得改变项。
6. 集群专属创意要求。

参考图只用于外观与明显可见结构，不自动产生容量、材质、认证、效果或营销声明。

### 4.6 AI Prompt 优化

用户点击“AI 优化”后创建异步 `prompt_job`，页面显示排队、分析中、待确认、失败或完成。

Prompt AI 一次接收：

- 当前集群最多 16 张参考图。
- 全局要求。
- 集群商品事实与要求。
- 平台、站点、语言和已发布规则版本。
- 输出模板中每张图的职责。

输出必须是受校验的结构化 JSON：

- 商品事实摘要。
- 仍缺失且不能猜测的信息。
- 商品身份锁。
- 每个输出槽位的消费者文案、画面设计和完整生图 Prompt。
- 合规警告。

AI 结果只是新 Prompt 草稿，不自动付费生图。用户确认后形成不可变 `prompt_version`。

首选 APIMart `/v1/responses` 的 `gpt-5` 多模态调用；模型名、超时和最大输出配置保存在服务端环境变量中。若契约测试失败，AI 优化按钮关闭，用户仍可手工填写 Prompt，不阻断基本生图流程。

### 4.7 生成预检

预检必须显示：

- 源图数量、TXT 数量和异常文件。
- 商品集群数量与每个集群参考图。
- 每个 TXT 的作用范围。
- 平台、站点、规则版本、比例和分辨率。
- 每套图的输出槽位及总任务数。
- 本人今日已用/剩余额度。
- 组织今日已用/剩余额度。
- 无法生成、缺资料和平台合规警告。

只有所有阻断错误清零并勾选付费确认后才能创建生成任务。重复点击确认只返回已有任务，不创建第二套。

### 4.8 实时任务页

前台不使用 WebSocket。可见页面每 3 秒请求一次批次快照；后台标签页降为每 15 秒，页面进入终态后停止轮询。请求携带版本号/ETag，无变化返回 `304`。

显示真实供应商进度；供应商没有百分比时只显示状态和已等待时间，不伪造进度。

单张状态：

```text
queued
→ preparing
→ submitting
→ submitted
→ processing
→ archiving
→ completed

queued → canceled
preparing/submitting/processing/archiving → failed
submitting → submit_unknown
```

批次状态：

```text
draft
→ uploading
→ organizing
→ ready
→ queued
→ running
→ completed | partial | needs_input | failed
```

取消只允许发生在供应商提交前。已有 `provider_task_id` 的任务不承诺取消。

### 4.9 结果与版本

- 每个输出槽位展示当前版本、历史版本、Prompt、参数和参考图快照。
- 技术完成与人工验收分开：`completed` 仅表示图片已归档；用户再标记 `accepted` 或 `rejected`。
- `rejected` 可填写原因并只重做这一张。
- 重做创建 `attempt + 1`，不覆盖旧图。
- 整批下载默认包含每个槽位最新的已通过版本；没有通过版本时包含最新完成版本并写入清单。
- ZIP 目录使用批次、集群、槽位和版本 ID，原文件名只作为展示信息。

## 5. 平台规则与输出模板

### 5.1 规则版本

平台规则和一套图模板都需要：

- `platform`、`market/site`、店铺类型。
- 规则来源 URL、核对日期和版本号。
- 图片数量、顺序、比例、分辨率。
- 主图与附图要求。
- 文案语言、禁止内容和人工审核提示。
- `draft/published/retired` 状态。

批次确认时保存规则版本快照；以后发布新规则不改变历史任务。

### 5.2 Shopee

Shopee 普通店与 Mall、不同站点规则不能混成一个通用模板。首版支持 SG、MY、TH、VN、PH、ID、TW、BR 八站配置，但生产模板必须在用户提供最终出图规范后由管理员发布。

默认 `1:1`；普通运营只选择平台/站点和已发布模板，不直接编辑合规规则。

### 5.3 TikTok Shop

TikTok Shop 不复用 Shopee 营销图模板。当前美国官方规则要求主图纯白背景、正面实物、至少 600×600，并限制添加文字、Logo、水印、边框和数字渲染。

因此：

- TikTok 主图默认走真实源图/标准化白底路线。
- AI 生成营销图标记“需人工合规审核”。
- 在目标国家/地区官方规则核对并发布前，TikTok 模板保持 `draft`，不能正式生成。

### 5.4 APIMart 参数

首版固定：

- `model=gpt-image-2`
- `n=1`
- `official_fallback=false`
- 默认 `size=1:1`
- 默认 `resolution=1k`

用户只能从管理员发布的允许组合中选择比例和分辨率，不能输入任意值。

APIMart 当前文档对 base64、`n` 和 4K 比例存在不一致：

- 参考图先使用官方上传接口取得 URL，不依赖 generation API 的 base64。
- `n` 固定为 1。
- 4K 默认关闭，完成真实契约测试后再由管理员启用允许组合。
- 同时兼容供应商 `processing` 和 `in_progress`，本地统一为 `processing`。

## 6. 容量、额度与公平调度

### 6.1 额度

- 组织级硬上限：每天 2,000 次生图提交尝试，按 Asia/Shanghai 自然日。
- 个人默认上限：每天 100 次；管理员可单独调整，但仍受组织上限限制。
- 单批最多 300 次。
- 明确重做也计入当日额度。
- Prompt AI 调用单独统计，不占图片生成额度。
- 已创建但尚未供应商提交的任务预占额度；取消后释放。
- 已发起供应商提交的任务不释放额度。

### 6.2 并发

生成 worker 只保留一个进程，但可同时持有多个供应商异步任务：

- 首次真实试用：`MAX_ACTIVE_GENERATIONS=2`。
- 契约与限流稳定后：提高到 5。
- 目标容量校准：提高到 8。
- 硬配置上限 12；只有 APIMart 明确支持且监控正常时才允许超过 8。

APIMart 文档给出的常见单张耗时约 30–60 秒，高分辨率可能更久。按 60 秒估算，并发 8 理论上约 480 张/小时，2,000 张约 4.2 小时；按 130 秒估算约 9 小时。实际吞吐必须以账号实测为准，不能仅凭服务器规格承诺。

供应商返回明确 `429` 时遵从重试时间并降低提交速率。提交网络超时且不知道是否受理时进入 `submit_unknown`，禁止自动重新 POST。

### 6.3 公平性

- 全局按创建时间排队。
- 每名用户同时最多占用 2 个活跃供应商任务。
- 管理员不能通过界面任意插队，首版不实现优先级队列。
- 队列暂停只阻止新提交，已有 `provider_task_id` 继续查询和归档。

## 7. 技术架构

### 7.1 技术栈

- Python 3.12。
- Django 5.2 LTS：登录、权限、CSRF、ORM、后台和模板。
- PostgreSQL 16：业务数据和数据库任务队列。
- Django 模板 + 原生 JavaScript：文件夹上传、拖拽和实时刷新。
- Pillow：实际图片格式验证和 EXIF 方向处理。
- Aliyun OSS SDK：预签名上传、归档和下载。
- Gunicorn：Web 进程。
- Docker Compose：部署。
- Caddy：临时反向代理和后续 HTTPS。

不使用 React、Node 宿主运行时、Redis 或第三方任务队列。

### 7.2 进程

```text
Caddy :18083
  → web（Django/Gunicorn）
      → PostgreSQL
      → OSS 预签名

prompt-worker
  → APIMart 多模态 Responses
  → PostgreSQL

generation-worker
  → APIMart 上传/生成/任务查询
  → OSS 归档
  → PostgreSQL
```

Prompt worker 与生图 worker 使用同一份代码镜像和不同启动命令。

### 7.3 数据模型

主要实体：

- `User`：Django 用户、角色、额度和是否必须改密。
- `Batch`：所有者、平台/站点、状态、规则版本和全局要求。
- `Asset`：原始图片/TXT、哈希、OSS 对象键、验证结果。
- `Cluster`：商品事实、身份锁、Prompt 覆盖和编辑版本。
- `ClusterAsset`：图片与集群关系、主图/补充图角色及顺序。
- `PromptJob`：AI 优化异步状态。
- `PromptVersion`：输入快照、模型、结构化输出和人工确认人。
- `RuleProfile`：平台规则版本。
- `OutputTemplate` 与 `OutputSlot`：一套图的职责与顺序。
- `Generation`：槽位、attempt、状态、完整 Prompt/参数/参考图快照和供应商 task ID。
- `ResultAsset`：供应商 URL、过期时间、OSS 归档信息、哈希和字节数。
- `AuditEvent`：登录和关键变更。

所有主键使用 UUID。文件名、数组索引和供应商 task ID 都不作为本平台业务主键。

关键唯一约束：

- 同一批次确认请求只能创建一次任务集合。
- `(cluster_id, output_slot_id, attempt)` 唯一。
- 一个 `provider_task_id` 只能绑定一个 Generation。
- 一个结果 OSS 对象键不可覆盖。

### 7.4 内部接口

页面使用同域内部 JSON API：

- 登录、退出、修改密码。
- 创建批次、取得上传签名、确认上传。
- 获取/更新集群、合并、拆分、切换主图。
- 分配 TXT 作用域。
- 创建和查询 Prompt 优化任务。
- 执行预检与确认生成。
- 获取带版本号的实时批次快照。
- 取消未提交任务。
- 单张重做与人工验收。
- 创建短时下载链接和整批 ZIP。

所有修改接口要求 CSRF、当前编辑版本和服务端对象权限检查。

## 8. APIMart 与 OSS 数据流

### 8.1 参考图

1. 浏览器通过精确对象键预签名 URL 上传私有 OSS。
2. 服务端验证大小、真实格式、解码和 EXIF。
3. 生成不可变标准参考副本。
4. 生图 worker 将标准副本上传 APIMart 官方上传接口，保存返回 URL。
5. 每个 generation 保存实际使用的 APIMart URL 与 OSS 对象快照。

### 8.2 提交

1. 数据库先创建 generation。
2. worker 将状态原子更新为 `submitting`。
3. POST APIMart。
4. 成功后立即保存 `provider_task_id` 和脱敏响应结构。
5. 网络超时且无 task ID 时标记 `submit_unknown`。
6. 有 task ID 后只查询，不重复 POST。

### 8.3 查询与归档

- 首次查询延迟 10 秒，随后每 5 秒查询。
- 优先使用经过契约测试的批量任务查询接口。
- `completed` 后扁平化全部 `result.images[*].url[*]`。
- 立即下载，校验 HTTP、MIME、像素、非空字节和哈希。
- 使用唯一 OSS 对象键归档。
- OSS 写入成功且读回元数据一致后才标记 `completed`。
- 归档失败保持 `archiving/failed`，不能把供应商临时 URL当作交付结果。

### 8.4 失败

- 一张失败不阻塞其他张。
- 一套有成功也有失败时，集群和批次为 `partial`。
- 明确 400/内容审核失败保存可理解原因，不自动重做。
- 明确 429/503 在未受理前按有限退避重试。
- POST 结果不确定时只允许管理员处理。
- 查询 GET 可安全重试。

## 9. 存储、历史与备份

OSS 使用现有桶的独立私有前缀，例如：

```text
independent-image-platform/
  originals/<batch>/<asset>
  normalized/<batch>/<asset>
  results/<batch>/<cluster>/<slot>/<attempt>/<result>
  exports/<batch>/<export>
  backups/postgres/<date>/<dump>
```

规则：

- 不复用旧飞书/Coze 对象键。
- 不覆盖历史对象。
- 操作员首版不能永久删除原图或结果。
- 批次“归档”只从默认列表隐藏。
- 元数据和文件默认长期保留，直到用户另行确认保留期限。
- 后台展示对象数量与估算存储量，避免无限增长失去可见性。

PostgreSQL：

- 每日一次逻辑备份到 OSS。
- 保留最近 30 个日备份和 12 个每月备份。
- 每月执行一次恢复演练到临时数据库并记录结果。

## 10. 安全

- 用户在聊天中公开过的 OSS AccessKey 视为泄露，实施前必须撤销并轮换。
- 新建最小权限 RAM 身份，只允许项目 OSS 前缀所需操作。
- APIMart Key、数据库密码和 Django Secret 只存服务器权限受控环境文件/Docker Secret。
- API Key 不进入前端、Prompt、日志、数据库错误文本或下载包。
- OSS 桶保持私有。
- 上传对象键由服务端生成，拒绝路径穿越。
- 实际解码图片，不信任扩展名或 Content-Type。
- 登录、修改集群、确认付费、重做、验收、规则发布和用户管理写入审计日志。
- 日志只记录 ID、状态、耗时和脱敏错误，不记录完整 Prompt、密码、Token 或签名 URL。
- 设置上传大小、请求频率、每日额度和并发限制。
- 正式环境启用 HTTPS、Secure/HttpOnly/SameSite Cookie、HSTS 和安全响应头。

## 11. 监控与运维

健康接口：

- `/health/live`：进程存活。
- `/health/ready`：数据库、worker 心跳和必要配置可用。

管理员仪表盘：

- 今日额度、队列深度和活跃任务。
- 完成、失败、部分成功和 `submit_unknown` 数。
- APIMart 429/5xx 数量。
- Prompt AI 成功率。
- 平均/P95 生成耗时和归档耗时。
- OSS 写入失败和数据库备份状态。
- generation worker 与 prompt worker 最后心跳。

Docker 日志按大小轮转。服务重启后 worker 扫描 `submitting/submitted/processing/archiving` 并恢复；`submit_unknown` 不自动恢复提交。

- 目录：`/opt/independent-image-platform`。

- 独立容器：`proxy`、`web`、`prompt-worker`、`generation-worker`、`postgres`。
- 独立网络、数据库卷和日志。
- 反向代理暂时绑定 `0.0.0.0:18083`。
- 数据库不映射公网端口。
- 容器使用 `restart: unless-stopped`。

任何部署、配置、凭证或端口变更按 Hermes 全局写操作执行，必须先取得 `.codex_locks/global.lock`。

### 12.3 发布

3. 备份数据库。
4. 上传新 Compose 配置和镜像。
5. 运行向前兼容迁移。
6. 启动新容器并检查 ready。
7. 从允许 IP 执行登录、上传、预检和假任务烟测。

回滚：

- 保留上一镜像 tag 和 Compose 配置。
- 数据库迁移首版只做向前兼容新增；不在同一版本删除列或表。
- 应用失败时恢复上一镜像，不覆盖数据库和 OSS 结果。

## 14. 分阶段实施顺序

### 阶段 0：安全与项目基线

- 轮换泄露的 OSS 凭证。
- 创建最小权限 RAM 身份和独立 OSS 前缀。
- 初始化 Git、依赖锁定、环境变量样例和 CI。

### 阶段 1：可点击原型

- 完成登录、批次列表、文件夹上传、集群拖拽、Prompt 编辑、预检和结果页。
- 使用固定假数据，不接 APIMart，不产生费用。

### 阶段 2：可靠任务核心

- PostgreSQL 数据模型、权限、预签名上传、文件验证。
- 数据库队列、假 Prompt/生图客户端、状态恢复和历史版本。
- 完成 100 用户/2,000 假任务容量验证。

### 阶段 3：Prompt AI

- 接 APIMart `gpt-5` 多模态 Responses。
- 结构化输出校验、缺资料提示、人工确认和版本快照。

### 阶段 4：真实 APIMart 单图

- 上传、`n=1` 提交、查询、归档和失败契约测试。
- 只跑一张已授权测试图。

### 阶段 5：批量与内部试用

- 先 5 名运营、组织每日 100 张、并发 2。
- 稳定后并发 5、组织每日 500 张。
- 记录图片可用率、失败率、平均耗时、P95 和实际费用。

### 阶段 6：目标容量

- 供应商验证通过后并发提高到 8。
- 组织上限提高到每日 2,000 张。
- 账号扩大到 100 人。
- 同时完成域名 HTTPS；没有 HTTPS 不进入这一阶段。
