# 独立批量出图平台完整设计

日期：2026-07-28  
状态：2026-07-29 已确认产品体验重设；本文保留后端安全、任务、存储和部署基线，前端流程以 `../research/2026-07-29-top-image-platform-redesign-research.md` 为准，协作与交付顺序以 `../superpowers/specs/2026-07-29-agent-orchestrated-delivery-design.md` 为准
目标读者：产品负责人、实现工程师、测试与运维人员

## 1. 结论

建设一套完全自有的公司内部批量出图平台，替代飞书与 Coze 提交、编排和取图链路。

系统核心不是“一个文件夹等于一个商品”，而是：

```text
上传批次 batch
  └─ 商品集群 cluster
      ├─ 一张主参考图
      ├─ 0–15 张同一可售 SKU 的补充参考图
      ├─ 商品事实与集群提示词
      └─ 一套输出槽位 generation
          └─ 每次重做形成新 attempt，旧版本永久保留
```

用户上传文件夹后，每张图片默认创建一个商品集群；这也是日常界面的唯一默认路径：一张图、一个 SKU、一键生成一整套图。只有运营主动进入“整理多图/变体”时，才可将其他图片标记为“同一可售 SKU 的补充参考”并合并为一套图；补充参考可以是不同角度或包装细节，但不默认包含不同颜色、花型、尺寸或款式。后者是独立子 SKU，默认各自生成一套图。

运营可将多个独立子 SKU 放入同一“商品家族”，用于在界面中归类、继承家族级 Brief 并一键批量提交；该能力默认折叠，不干扰单图流程。商品家族不合并商品身份：每个子 SKU 仍保留自己的主参考图、身份锁、白底首图、审核与整套输出。

首版面向最多约 100 名内部员工，组织级每日最多接收 2,000 次生图提交尝试。系统本身按该规模设计；APIMart 账号的真实并发和限流未公开，正式承诺“当天全部完成”以前必须通过分阶段契约测试确认供应商吞吐。

## 2. 已冻结范围

### 2.1 首版包含

- 管理员创建、停用和重置内部员工账号。
- 管理员与运营两种角色。
- 运营只能访问本人批次、图片、Prompt 和结果；管理员可查看全部。
- Chrome/Edge 文件夹拖拽或文件夹选择上传。
- 每张图片默认一个商品集群；日常操作直接一图一 SKU 出整套图，多图关系整理为可选展开能力。
- 拖拽合并、移出、调整主图和补充参考图；不同颜色、花型、尺寸或款式保持为独立子 SKU。
- 全局提示词、集群提示词、商品事实和不得改变项。
- 多个 TXT 导入、作用域建议、人工确认和修改。
- AI 商品资料整理、Prompt 优化和一套图策划。
- 竞品图片分析为可追溯的 Style DNA：可复用画面层级、版式结构、镜头、色彩、光线与场景密度，但竞品原图不作为生成参考。
- Shopee/TikTok 平台规则配置和版本快照。
- 生成前付费任务预检与二次确认。
- APIMart 异步提交、状态查询、结果下载和 OSS 归档。
- 单张失败只重做该张，旧结果和旧 Prompt 保留。
- 批次、集群、单张和版本级实时状态。
- 结果预览、人工通过/不通过、单张下载和整批 ZIP。
- 组织与个人每日额度。
- 审计日志、运行指标、备份和恢复。

### 2.2 首版不包含

- 飞书、Coze 或旧工作流兼容层。
- 公开注册、短信验证码、第三方客户租户和在线收费。
- 通用工作流编辑器。
- 在线 PS、画布或像素级图片编辑。
- 多模型自由切换。
- 自动无限重试。
- Webhook；首版使用 APIMart 任务查询。
- Redis、RabbitMQ、微服务或 Kubernetes。
- 普通运营编辑平台合规规则。
- 删除历史结果；首版只允许归档隐藏。

## 3. 用户、登录与权限

### 3.1 账号

- 不提供公开注册。
- 登录使用 ERP 账号密码校验；所有 ERP 登录成功用户都可进入平台。
- 平台为 ERP 登录用户自动创建本地影子用户，用于项目归属、对象权限、审计和角色判断；本地影子用户不保存 ERP 密码，密码字段设为不可用。
- 刘学城是首位且唯一初始管理员；管理员身份由服务器环境变量 `PLATFORM_ADMIN_ERP_USERS` 中的 ERP 登录名决定，其他 ERP 用户默认为 `operator`。
- ERP Token 只保存在服务端 session 中，浏览器只持有 Django session Cookie；退出或 Token 过期后需要重新 ERP 登录。
- 不使用来源 IP 白名单；连续 5 次失败后锁定账号 15 分钟，避免公网入口被分布式来源绕过。
- 登录会话有效期 12 小时；退出、停用账号或管理员强制注销后立即失效。

### 3.2 角色

`operator`：

- 只能创建和查看自己的批次。
- 可整理集群、编辑资料、生成、重做、验收和下载自己的结果。
- 不能修改额度、用户、平台规则或系统参数。

`admin`：

- 查看全部批次和系统指标。
- 调整平台管理员名单、停用影子账号和强制注销会话。
- 调整个人额度、暂停队列、处理 `submit_unknown`。
- 发布平台规则和输出模板。
- 不可直接修改已经提交任务的 Prompt/参考图快照。

### 3.3 对象级隔离

所有批次、资源、集群、Prompt 版本和生成记录都带 `owner_id` 或从所属批次推导所有者。每个查询和修改接口都在服务端按当前用户过滤，不能依赖前端隐藏。

下载图片不返回公开永久 URL。平台验证权限后通过 Django 授权代理读取私有对象，或生成短时 OSS 签名下载地址。

### 3.4 临时 IP 入口

服务器当前 `18081` 和 `18082` 已占用，`18083` 在 2026-07-28 的只读核查中空闲。

临时试用：

- 使用 `http://<服务器>:18083`。
- 不使用来源 IP 白名单；只使用临时测试账号和非敏感测试素材。
- 不允许把该入口视为正式生产登录入口。

正式员工上传真实商品素材前必须切换域名 HTTPS；届时启用 `Secure` Cookie、HSTS 和标准 443 入口。没有 HTTPS 时不扩大到 100 人。

## 4. 产品信息架构与实时交互

### 4.1 页面

1. 登录页。
2. 生产工作台。
3. 新建项目：SKU 导入（首选）与文件夹补充上传。
4. 商品确认板。
5. 商品创作台与一套图策划。
6. 生产队列与生成预检。
7. 审核中心与导出中心。
8. 模板/规则中心与系统管理。

### 4.2 生产工作台

工作台显示：

- 最近项目、平台、站点和创建时间。
- 商品数、计划图片数与套图完成度。
- 已完成、生成中、失败、待审核和待补资料数量。
- 组织队列位置、异常和更新时间。

筛选：草稿、排队中、生成中、待审核、部分完成、已完成、需处理、已归档。

### 4.3 导入与上传

- SKU 导入是首选入口：浏览器只把 SKU 交给平台 API，服务端登录内部商品资料服务并归档商品名和主图。
- 使用 `<input webkitdirectory multiple>` 和拖放区域保留相对路径。
- 浏览器先把文件清单发送给服务端，服务端返回逐文件、短时、精确对象键的 OSS 预签名上传地址。
- 浏览器直接上传 OSS，显示每个文件与整个批次的进度。
- 上传完成后服务端逐个执行 HEAD 校验，再进行实际格式验证。
- 页面刷新或断网后可继续未完成文件，不重复上传已验证对象。

首版限制：

- 图片：JPEG、PNG；单张不超过 20 MB。
- TXT：UTF-8，单个不超过 256 KB。
- 单批最多 100 张源图片、20 个 TXT。
- 单商品集群最多 16 张参考图。
- 单批预检后最多创建 300 个生图任务。
- 不支持 ZIP、PSD、PDF、视频、HEIC 或可执行文件。

原图保留不变；系统另建已校正 EXIF 方向的标准参考副本。服务端生成对象键，不使用用户文件名作为存储路径。

### 4.4 商品集群工作台

- 上传完成后每张有效图片创建一个独立商品集群。
- 图片卡片可拖入其他集群；拖入时运营明确选择“同一可售 SKU 的补充参考”后才合并。不同颜色、花型、尺寸或款式保持独立集群，分别生产自己的套图。
- 运营可把多个独立集群放入一个可选商品家族；“生成整个家族”对其中每个子 SKU 分别执行预检和生成，任一子 SKU 的失败不阻塞其他子 SKU。
- 集群必须保留一张主参考图。
- 支持从集群移出图片；移出后自动形成新的独立集群。
- 合并、拆分和切换主图只影响尚未确认的新版本，不修改已提交生成任务的历史快照。
- 同一商品集群超过 16 张时禁止生成并提示移除。
- 系统可建议疑似相同商品，但首版绝不自动合并。

并发编辑使用整数 `version`。保存时提交上次读取的版本；版本不一致返回冲突并要求刷新，避免两个标签页相互覆盖。

### 4.5 TXT 与提示词作用域

TXT 是提示词资料来源，不是任务主键。

- 根目录 TXT 默认建议为全局资料。
- 与图片同名的 TXT 默认建议分配给该图片初始集群。
- 其他 TXT 显示为“待分配资料”。
- 多个 TXT 不自动拼接；用户必须确认其作用于全局或一个/多个集群。
- 文件内容导入编辑器后保留来源文件名和原始文本快照。

最终输入分为：

1. 全局创意与品牌要求。
2. 商品名称和品类。
3. 已确认事实：卖点、规格、材质、包装内容、使用方法。
4. 商品身份硬约束：颜色、Logo、结构、部件数量、接口和连接关系。
5. 禁用内容、敏感声明和不得改变项。
6. 集群专属创意要求。

参考图只用于外观与明显可见结构，不自动产生容量、材质、认证、效果或营销声明。

### 4.6 AI Prompt 优化

用户点击“AI 优化”后创建异步 `prompt_job`，页面显示排队、分析中、待确认、失败或完成。

`prompt_job` 先调用 APIMart 多模态 Responses 的 `gpt-5-nano-2025-08-07`，将图片转换为受限 `VisualFactPacket`；之后才调用 `deepseek-v4-pro`。文本模型一次接收：

- 当前集群最多 16 张我方参考图的视觉事实包。
- 全局要求。
- 集群商品事实与要求。
- 平台、站点、语言和已发布规则版本。
- 输出模板中每张图的职责。

竞品图的观察请求只允许输出抽象 Style DNA 候选（色彩、光线、构图、场景密度等），不得输出或传递竞品商标、包装文字、人物、独特插画或可识别版式。竞品原图只到 `gpt-5-nano-2025-08-07`，不进入 `deepseek-v4-pro`、`gpt-image-2`、生产 Prompt、生成任务或导出包。

输出必须是受校验的结构化 JSON：

- 商品事实摘要。
- 仍缺失且不能猜测的信息。
- 商品身份锁。
- 每个输出槽位的消费者文案、画面设计和完整生图 Prompt。
- 合规警告。

AI 结果只是新 Prompt 草稿，不自动付费生图。用户确认后形成不可变 `prompt_version`。

APIMart 多模态 Responses 的 `gpt-5-nano-2025-08-07` 是唯一视觉观察器，只产生后端 Schema 校验后的 `VisualFactPacket`；经 APIMart 网关的 `deepseek-v4-pro` Chat Completions 承担所有文本语义节点；APIMart 的 `gpt-image-2` 只承担图片生成和局部修订。模型名、网关、超时和最大输出配置保存在服务器受限环境变量中。APIMart 中文文档与账户契约测试是唯一接入事实来源：必须验证三个精确模型 ID、图片输入、结构化输出封装、超时、内容安全错误、限流与脱敏日志。任一模型未开通、模型未知或输出不符合契约时，系统关闭依赖它的自动节点，不得降级为 V3 或其他模型；员工仍可填写结构化商品资料，但不提交未通过预检的生图任务。上游模型文档只能作能力参考，不能推断 APIMart 的模型可用性、参数或响应格式。

### 4.7 生成预检

预检必须显示：

- 源图数量、TXT 数量和异常文件。
- 商品集群数量与每个集群参考图。
- 每个 TXT 的作用范围。
- 平台、站点、规则版本、比例和分辨率。
- 每套图的输出槽位及总任务数。
- 本人今日已用/剩余额度。
- 组织今日已用/剩余额度。
- 无法生成、缺资料和平台合规警告。

只有所有阻断错误清零并勾选付费确认后才能创建生成任务。重复点击确认只返回已有任务，不创建第二套。

### 4.8 实时任务页

前台不使用 WebSocket。可见页面每 3 秒请求一次批次快照；后台标签页降为每 15 秒，页面进入终态后停止轮询。请求携带版本号/ETag，无变化返回 `304`。

显示真实供应商进度；供应商没有百分比时只显示状态和已等待时间，不伪造进度。

单张状态：

```text
queued
→ preparing
→ submitting
→ submitted
→ processing
→ archiving
→ completed

queued → canceled
preparing/submitting/processing/archiving → failed
submitting → submit_unknown
```

批次状态：

```text
draft
→ uploading
→ organizing
→ ready
→ queued
→ running
→ completed | partial | needs_input | failed
```

取消只允许发生在供应商提交前。已有 `provider_task_id` 的任务不承诺取消。

### 4.9 结果与版本

- 每个输出槽位展示当前版本、历史版本、Prompt、参数和参考图快照。
- 技术完成与人工验收分开：`completed` 仅表示图片已归档；用户再标记 `accepted` 或 `rejected`。
- `rejected` 可填写原因并只重做这一张。
- 重做创建 `attempt + 1`，不覆盖旧图。
- 整批下载默认包含每个槽位最新的已通过版本；没有通过版本时包含最新完成版本并写入清单。
- ZIP 目录使用批次、集群、槽位和版本 ID，原文件名只作为展示信息。

## 5. 平台规则与输出模板

### 5.1 规则版本

平台规则和一套图模板都需要：

- `platform`、`market/site`、店铺类型。
- 规则来源 URL、核对日期和版本号。
- 图片数量、顺序、比例、分辨率。
- 主图与附图要求。
- 文案语言、禁止内容和人工审核提示。
- `draft/published/retired` 状态。

所有平台模板的第 1 槽均为不可删除的“标准白底产品主图”：完整、真实、准确呈现实际售卖商品，无促销文字、无水印、无边框和无关图形；它先于任何营销场景、模特或信息图生成。平台与市场规则只能进一步收紧该槽位，不能把它替换成营销图。

调度器按同一批次、商品集群和输出模板建立顺序门禁：第 2–8 槽在第 1 槽处于排队、提交、处理中、失败或取消时保持排队；仅当第 1 槽技术状态为完成才可调用生图供应商。主图失败或取消只需重做该主图，原有后续槽位不标记为失败、不额外占用重做额度；白底图重做完成后继续执行。仅在同一模板主图记录根本不存在的异常状态下，后续槽位标记为前置条件失败且不调用供应商。不同模板、不同商品集群或不同批次的主图不能解除该门禁。

批次确认时保存规则版本快照；以后发布新规则不改变历史任务。

### 5.2 Shopee

Shopee 普通店与 Mall、不同站点规则不能混成一个通用模板。首版支持 SG、MY、TH、VN、PH、ID、TW、BR 八站配置；默认套图为 8 张、`1:1`、`1k`，但运营可以从 APIMart 与当前已发布模板共同允许的参数中选择覆盖。第 1 张遵从全平台标准白底主图；其余槽位可放入经事实校验的卖点、尺寸、用法或对比信息。

普通运营只选择平台/站点和已发布模板，不直接编辑合规规则。Shopee 的当前官方运营资料将 1:1、至少 1024×1024、真实商品、白底主图、无水印，以及尺寸/成分/用法等信息图列为推荐方向；每站最终规则仍按来源版本发布。

### 5.3 TikTok Shop

TikTok Shop 不复用 Shopee 营销图模板。当前美国官方规则要求主图纯白背景、正面实物、至少 600×600，并限制添加文字、Logo、水印、边框和数字渲染。

因此：

- TikTok 第 1 张直接采用全平台标准白底主图规则，并额外受 TikTok 站点限制约束。
- TikTok 第 2–8 张可按已发布站点规则叠加经事实校验的本地化文字；AI 生成营销图标记“需人工合规审核”。
- 在目标国家/地区官方规则核对并发布前，TikTok 模板保持 `draft`，不能正式生成。

文案语言默认由站点映射：SG/PH/US 使用英语，MY 使用马来语，TH 使用泰语，VN 使用越南语，ID 使用印尼语，TW 使用繁体中文，BR 使用巴葡；运营可在审核前选择已发布的替代语言。所有图中文字都必须可追溯到商品事实和站点规则快照。

### 5.4 APIMart 参数

首版固定：

- `model=gpt-image-2`
- `n=1`
- `official_fallback=false`
- 默认 `size=1:1`
- 默认 `resolution=1k`

用户只能从管理员发布的允许组合中选择比例和分辨率，不能输入任意值。

APIMart 当前文档对 base64、`n` 和 4K 比例存在不一致：

- 参考图先使用官方上传接口取得 URL，不依赖 generation API 的 base64；`gpt-image-2` 当前账户实测要求 `image_urls` 为 URL 字符串数组。
- `n` 固定为 1。
- 4K 默认关闭，完成真实契约测试后再由管理员启用允许组合。
- 同时兼容供应商 `pending`、`processing` 和 `in_progress`，本地统一为 `processing`。

## 6. 容量、额度与公平调度

### 6.1 额度

- 组织级硬上限：每天 2,000 次生图提交尝试，按 Asia/Shanghai 自然日。
- 不设置面向运营的固定个人日额度；所有用户共同受组织级上限限制，由公平调度避免单人耗尽活跃资源。
- 单批最多 300 次。
- 明确重做也计入当日额度。
- Prompt AI 调用单独统计，不占图片生成额度。
- 已创建但尚未供应商提交的任务预占额度；取消后释放。
- 已发起供应商提交的任务不释放额度。

### 6.2 并发

生成 worker 只保留一个进程，但可同时持有多个供应商异步任务：

- 首次真实试用：`MAX_ACTIVE_GENERATIONS=2`。
- 契约与限流稳定后：提高到 5。
- 逐级压测通过后提高到 8、50、100。
- APIMart API 的配置硬上限为 **500 个活跃异步任务**；`MAX_ACTIVE_GENERATIONS` 必须在 `1..500` 内。500 是供应商 API 并发上限，不等于单台服务器、单个 worker 或单个用户可同时提交 500 个请求。
- 到达 500 前，每级都必须验证无重复提交、429/5xx 退避、归档完整、P95 延迟、数据库连接与内存；任一指标退化立即降回上一级。

当前 worker 尚未实现跨进程原子认领和 `MAX_ACTIVE_GENERATIONS` 的实际限流，因此在该门禁实现、真实契约测试和监控完成前，运行配置维持 `2`，不得直接设为 500 或宣称已经具备 500 并发能力。

供应商返回明确 `429` 时遵从重试时间并降低提交速率。提交网络超时且不知道是否受理时进入 `submit_unknown`，禁止自动重新 POST。

### 6.3 公平性

- 全局按创建时间与用户公平轮转排队。
- 每名用户基础占用 2 个活跃供应商任务；有空闲容量时可临时借用更多槽位。其他用户出现待处理任务时，系统停止为已借用用户分配新槽位，优先恢复公平轮转；已提交给供应商的任务不强制取消。
- 管理员不能通过界面任意插队；动态借用由队列服务决定并记录审计事件。
- 队列暂停只阻止新提交，已有 `provider_task_id` 继续查询和归档。

## 7. 技术架构

### 7.1 技术栈

- Python 3.12。
- Django 5.2 LTS：登录、权限、CSRF、ORM、后台和模板。
- PostgreSQL 16：业务数据和数据库任务队列。
- React + TypeScript + Vite：运营工作台、文件夹上传、拖拽、实时刷新和审核；Django 提供同源 API、Session 和 CSRF。
- Pillow：实际图片格式验证和 EXIF 方向处理。
- Aliyun OSS SDK：预签名上传、归档和下载。
- Gunicorn：Web 进程。
- Docker Compose：部署。
- Caddy：临时反向代理和后续 HTTPS。

不使用 React、Node 宿主运行时、Redis 或第三方任务队列。

### 7.2 进程

```text
Caddy :18083 / 443
  → React 静态工作台
  → /api、/admin、/auth → web（Django/Gunicorn）
      → PostgreSQL
      → OSS 预签名

prompt-worker
  → APIMart `gpt-5-nano-2025-08-07` Multimodal Responses → VisualFactPacket（仅视觉观察）
  → APIMart `deepseek-v4-pro` Chat Completions（仅文本推理；均在契约验证后）
  → PostgreSQL

generation-worker
  → APIMart 上传/生成/任务查询
  → OSS 归档
  → PostgreSQL
```

Prompt worker 与生图 worker 使用同一份代码镜像和不同启动命令。React 构建产物由 Caddy 提供，生产不运行 Node 前端服务器。

### 7.3 数据模型

主要实体：

- `User`：Django 影子用户、ERP 登录名、角色、额度和对象权限归属。
- `Batch`：所有者、平台/站点、状态、规则版本和全局要求。
- `Asset`：原始图片/TXT、哈希、OSS 对象键、验证结果。
- `Cluster`：商品事实、身份锁、Prompt 覆盖和编辑版本。
- `ProductFamily`：可选的同款变体管理与批量提交分组；不共享子 SKU 的生成身份或结果。
- `ClusterAsset`：图片与集群关系、主图/补充图角色及顺序。
- `VisualObservation`：资产类型、模型快照、输入资产快照、Schema 校验结果与不可变 `VisualFactPacket`；竞品包仅有抽象 Style DNA 字段。
- `PromptJob`：AI 优化异步状态。
- `PromptVersion`：输入快照、模型、结构化输出和人工确认人。
- `RuleProfile`：平台规则版本。
- `OutputTemplate` 与 `OutputSlot`：一套图的职责与顺序。
- `Generation`：槽位、attempt、状态、完整 Prompt/参数/参考图快照和供应商 task ID。
- `ResultAsset`：供应商 URL、过期时间、OSS 归档信息、哈希和字节数。
- `AuditEvent`：登录和关键变更。

所有主键使用 UUID。文件名、数组索引和供应商 task ID 都不作为本平台业务主键。

关键唯一约束：

- 同一批次确认请求只能创建一次任务集合。
- `(cluster_id, output_slot_id, attempt)` 唯一。
- 一个 `provider_task_id` 只能绑定一个 Generation。
- 一个结果 OSS 对象键不可覆盖。

### 7.4 内部接口

页面使用同域内部 JSON API：

- ERP 登录、退出和会话失效。
- 创建批次、取得上传签名、确认上传。
- 获取/更新集群、合并、拆分、切换主图。
- 分配 TXT 作用域。
- 创建和查询 Prompt 优化任务。
- 执行预检与确认生成。
- 获取带版本号的实时批次快照。
- 取消未提交任务。
- 单张重做与人工验收。
- 创建短时下载链接和整批 ZIP。

所有修改接口要求 CSRF、当前编辑版本和服务端对象权限检查。

## 8. APIMart 与 OSS 数据流

### 8.1 参考图

1. 浏览器通过精确对象键预签名 URL 上传私有 OSS。
2. 服务端验证大小、真实格式、解码和 EXIF。
3. 生成不可变标准参考副本。
4. Prompt worker 可将我方标准副本或私有竞品图传给 `gpt-5-nano-2025-08-07`，只保存 Schema 校验后的视觉事实包；竞品原图不进入后续 Prompt 或生成路径。
5. 生图 worker 仅将我方标准副本上传 APIMart 官方上传接口，保存返回 URL。
6. 每个 generation 保存实际使用的 APIMart URL 与 OSS 对象快照。

### 8.1.1 SKU 商品资料导入

SKU 导入是上传图片之外的一级输入来源。用户登录平台时先通过 ERP 登录入口取得运行时 Token，平台仅把该 Token 保存在服务端 session 中；SKU 查询再以当前登录用户的 Token 作为 `Authorization` 调用 `CATALOG_QUERY_URL`。浏览器不接触 ERP Token、商品资料服务地址、OSS 凭据或供应商密钥。

当前后端入口为 `POST /api/projects/{id}/sku-import/`，只接收 `{"skus": ["..."]}`，默认每请求最多 50 个输入项；项目已有确认键或生成历史时拒绝写入。响应只返回每项的 SKU、商品名、导入状态、商品卡 ID 和受控错误码。真实发布前必须确认 ERP 登录响应中的 Token 字段、有效期和失效语义；Token 缺失或过期时返回登录失效，用户重新登录后再导入。

查询请求只发送 `{"skuList": ["..."]}`；响应只消费输入 SKU、`data[].productName` 与 `data[].pic`。SKU 仅用于审计、去重与重导入，商品名用于界面命名，图片由服务端下载、实际解码校验并归档为私有参考图。销售、库存、成本、分类和其他返回字段一律忽略，不进入前端状态、数据库业务字段或任何 Prompt。

商品资料服务返回的图片 URL 不是交付资产：下载只允许配置为精确公网 IPv4/IPv6 字面量的图片源，主机名、私网/保留/回环/组播地址和任一不在名单内的重定向均拒绝；同时限制重定向、大小、格式和像素，并在归档成功后使用私有副本。成功包络中的空数据才标记 `sku_not_found`；查询的网络、HTTP、JSON 或包络异常统一为 `catalog_unavailable`。图片或归档失败只标记对应 SKU 失败，不阻塞同批其他 SKU，也不暴露原始 URL、Token 或供应商响应。

### 8.2 提交

1. 数据库先创建 generation。
2. worker 将状态原子更新为 `submitting`。
3. POST APIMart。
4. 成功后立即保存 `provider_task_id` 和脱敏响应结构。
5. 网络超时且无 task ID 时标记 `submit_unknown`。
6. 有 task ID 后只查询，不重复 POST。

### 8.3 查询与归档

- 首次查询延迟 10 秒，随后每 5 秒查询。
- 优先使用经过契约测试的批量任务查询接口。
- `completed` 后扁平化全部 `result.images[*].url[*]`。
- 立即下载，校验 HTTP、MIME、像素、非空字节和哈希。
- 使用唯一 OSS 对象键归档。
- OSS 写入成功且读回元数据一致后才标记 `completed`。
- 归档失败保持 `archiving/failed`，不能把供应商临时 URL当作交付结果。

### 8.4 失败

- 一张失败不阻塞其他张。
- 一套有成功也有失败时，集群和批次为 `partial`。
- 明确 400/内容审核失败保存可理解原因，不自动重做。
- 明确 429/503 在未受理前按有限退避重试。
- POST 结果不确定时只允许管理员处理。
- 查询 GET 可安全重试。

## 9. 存储、历史与备份

OSS 使用现有桶的独立私有前缀，例如：

```text
independent-image-platform/
  originals/<batch>/<asset>
  normalized/<batch>/<asset>
  results/<batch>/<cluster>/<slot>/<attempt>/<result>
  exports/<batch>/<export>
  backups/postgres/<date>/<dump>
```

规则：

- 不复用旧飞书/Coze 对象键。
- 不覆盖历史对象。
- 操作员首版不能永久删除原图或结果。
- 批次“归档”只从默认列表隐藏。
- 原图、生成结果、审核批注、Brief 与 Prompt 版本永久保留；批次“归档”只从默认列表隐藏。
- 后台展示对象数量与估算存储量，避免无限增长失去可见性。

PostgreSQL：

- 每日一次逻辑备份到 OSS。
- 保留最近 30 个日备份和 12 个每月备份。
- 每月执行一次恢复演练到临时数据库并记录结果。

## 10. 安全

- OSS AccessKey、APIMart Key、ERP 密码、数据库密码和 Django Secret 只存服务器权限受控环境文件/Docker Secret。
- OSS 凭据应只允许项目 OSS 前缀所需操作。
- API Key 不进入前端、Prompt、日志、数据库错误文本或下载包。
- OSS 桶保持私有。
- 上传对象键由服务端生成，拒绝路径穿越。
- 实际解码图片，不信任扩展名或 Content-Type。
- 登录、修改集群、确认付费、重做、验收、规则发布和用户管理写入审计日志。
- 日志只记录 ID、状态、耗时和脱敏错误，不记录完整 Prompt、密码、Token 或签名 URL。
- 设置上传大小、请求频率、每日额度和并发限制。
- 正式环境启用 HTTPS、Secure/HttpOnly/SameSite Cookie、HSTS 和安全响应头。

- APIMart/OSS/ERP 凭据的服务器 Secret 配置方式；凭据值不能进入仓库、文档、前端、日志或导出包。

这些内容由管理员规则配置承接，不需要修改任务核心架构。
