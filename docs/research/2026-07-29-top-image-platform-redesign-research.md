# 顶级 AI 商品出图平台调研与产品重设

日期：2026-07-29
状态：产品方向已确认；作为前端与流程的体验基线，后续按 Agent 协作交付设计进入实施
适用范围：公司内部 AI 商品图平台的前端、流程、信息架构和核心产品体验

## 1. 结论

当前 MVP 方向不够好。它只是把后端任务链路做成了页面：批次、集群、提示词、预检、JSON 状态。这能证明技术流程跑通，但不像一个真正给运营使用的出图平台。

新的目标不是“上传文件后跑一批任务”，而是：

```text
项目/活动
  → 商品素材库
  → 商品分组与资料补全
  → 套图方案选择
  → 可视化创作台
  → 批量生产队列
  → 审核、重做、导出
```

前端必须围绕运营人员的真实心智设计：他们关心商品、平台、套图、审核和交付，不关心后台 batch、cluster、generation、attempt。

  <https://claid.ai/>

## 3. 顶级平台的共性

### 3.1 不是表单，而是工作台

优秀平台的第一视角通常是“我正在编辑哪个商品、要产出哪组图”。页面会给用户一个明显的视觉中心：商品预览、场景预览、生成结果网格或画布。

我们的旧页面把 JSON 状态、批次字段和按钮堆在一起，用户没有“我在做图”的感觉。

### 3.2 模板和风格先行

Photoroom、Pebblely、Pixelcut、Flair 都会把 style、template、scene、photoshoot 作为入口，降低用户写提示词的负担。

我们的旧页面把“提示词文本框”放得太靠前。正确做法是让用户先选：

- 平台：Shopee / TikTok Shop。
- 站点：SG / MY / TH / VN / PH / ID / TW / BR 等。
- 套图模板：主图、卖点图、场景图、细节图、尺寸图、包装图、广告图。
- 风格：白底、家居、户外、节日、科技、极简、质感棚拍等。
- 比例和分辨率：只展示 APIMart 当前允许组合。

提示词应该由 AI 根据商品资料、平台规则和模板自动生成，用户负责确认和微调。

### 3.3 商品身份锁比“创意自由”更重要

电商图不是纯创意图。Claid 和 WizStudio 都强调商品准确、Logo/细节保持、批量一致性。TikTok/Shopee 规则也要求商品真实清晰。

因此界面要把“不得改变项”做成一等公民：

- 颜色。
- Logo。
- 结构。
- 配件数量。
- 包装文字。
- 接口、按钮、零件位置。
- 尺寸比例。

这些不能藏在一个自由文本框里。

### 3.4 批量生产必须可见、可控、可重做

顶级平台都在弱化单张手工操作，同时保留单张修正能力。我们的业务每天可能 2,000 张图，所以核心不是做一个漂亮单图编辑器，而是做“批量生产 + 单张异常处理”。

必须有：

- 全局队列。
- 每个商品的进度。
- 每个输出槽位的进度。
- 失败原因。
- 只重做失败项。
- 历史版本对比。
- 审核通过/驳回。
- 按平台导出。

### 3.5 合规规则应当在生成前和审核时都出现

TikTok Shop 对主图白底、最小分辨率、禁用水印/边框/促销文字等有明确约束。Shopee 不同站点和店铺类型也不能混成一个模板。

所以平台规则不能只是后台文档，要体现在：

- 创建项目时选择平台/站点。
- 选择套图模板时展示规则摘要。
- 预检时提示阻断项和风险项。
- 审核时按图片槽位显示 checklist。
- 导出时按平台命名和打包。

## 4. 新的信息架构

左侧主导航建议如下：

```text
工作台
素材库
商品项目
生产队列
审核中心
导出记录
模板中心
系统管理
```

关键对象重命名：

| 旧技术词 | 新前端词 | 说明 |
| --- | --- | --- |
| Batch | 项目 / 出图项目 | 一次业务活动或上传任务 |
| Cluster | 商品 / SKU 分组 | 默认一张图一个商品，可拖拽合并多角度 |
| Generation | 输出图 / 槽位任务 | 主图、场景图、细节图等 |
| Attempt | 版本 / 重做版本 | 每次重做保留历史 |
| Prompt | 创意 brief / 生图指令 | 用户看到结构化 brief，完整 prompt 可折叠 |
| RuleProfile | 平台规则 | Shopee/TikTok 的规则版本 |
| OutputTemplate | 套图模板 | 每套图包含哪些槽位、比例、用途 |

## 5. 目标流程

### 5.1 项目首页

用户登录后看到的不是批次列表，而是生产控制台：

- 今日生成额度、排队中、生成中、待审核、失败数。
- 最近项目卡片。
- “新建出图项目”主按钮。
- 生产异常提示。
- 我的待审核任务。

管理员多看到：

- 全公司今日用量。
- APIMart 错误率。
- 队列深度。
- 供应商限流。
- worker 心跳。

### 5.2 新建项目

步骤：

1. 项目名称。
2. 平台和站点。
3. 套图模板。
4. 比例/分辨率。
5. 导入方式：粘贴 SKU（首选）、拖拽/选择文件夹（补充）、补充 TXT 种子风格。

上传后不立即生成。先进入“识别和分组”。

### 5.3 识别和分组

核心体验：

- 顶部显示识别结果：图片数、TXT 数、默认商品数、疑似异常。
- 中间是商品卡片瀑布流/网格。
- 每张图默认一个商品卡。
- 多角度图可以拖到同一商品卡，变成一组参考图。
- 每个商品卡显示主图、补充角度、商品资料完整度、规则风险。
- TXT 作为“资料卡”出现，可拖到全局或某个商品。

禁止展示 raw cluster ID，除非在管理员调试面板。

### 5.4 商品资料与 AI Brief

每个商品卡进入详情后，右侧是结构化信息：

- 商品名称。
- 品类。
- 卖点。
- 规格。
- 材质。
- 颜色。
- 使用场景。
- 不得改变项。
- 禁用内容。
- 备注。

AI 按这些字段生成 brief，不直接让用户面对长 prompt。

输出给用户看的结构：

- 商品理解。
- 缺失信息。
- 身份锁。
- 每张图的画面方案。
- 平台合规提醒。
- 可折叠完整 prompt。

### 5.5 创作台

创作台是新前端的核心页面：

```text
左侧：商品参考图、资料、身份锁
中间：当前输出图预览 / 对比 / 版本
右侧：套图槽位、风格模板、比例、AI brief、生成按钮
底部：同商品所有输出图缩略图与状态
```

首版不做完整 PS 级画布。只做商品图创作台：

- 预览源图。
- 预览已生成结果。
- 切换输出槽位。
- 选择模板/风格。
- 改 brief。
- 生成、重做、接受、驳回。

只有当业务明确需要自由摆放道具、文本、图层时，再升级到真正画布。否则画布会拖慢交付。

### 5.6 批量生产

批量生产页要像生产队列，不像日志页。

每行一个商品，列为：

- 商品主图。
- 套图完成度。
- 主图状态。
- 场景图状态。
- 细节图状态。
- 失败原因。
- 当前耗时。
- 操作：暂停未提交、只重做失败、进入审核。

顶部显示：

- 已完成 / 总任务。
- 生成中。
- 排队中。
- 失败。
- 今日额度剩余。
- 预计完成时间。

### 5.7 审核中心

审核页按“需要人工判断”的任务组织，而不是按技术状态组织：

- 待审核。
- 被驳回。
- 已通过。
- 需要补资料。

单张审核要显示：

- 源图与结果图对比。
- 使用的平台规则 checklist。
- 商品身份锁 checklist。
- prompt/参数/版本。
- 通过。
- 驳回并填写原因。
- 重做当前槽位。

### 5.8 导出

导出不是简单下载全部图片。应按平台交付：

- Shopee 八站包。
- TikTok Shop 包。
- 自定义 ZIP。
- 只导出已通过。
- 只包含审核通过的最新版本；未通过、失败和旧版本不进入交付包。
- ZIP 按 `商品名称__SKU/01–08 槽位` 组织，并附导出清单。

## 6. 页面原型方向

### 6.1 视觉风格

定位是公司内部生产工具，不是营销官网。

建议风格：

- 深浅皆可，首版建议浅色生产后台。
- 左侧固定导航。
- 顶部项目/平台/额度状态条。
- 卡片式商品网格。
- 大缩略图。
- 状态 chip。
- 进度条。
- 右侧参数抽屉。
- 折叠高级 prompt。
- 不展示 JSON。

### 6.2 第一优先级页面

重做前端时先做 5 个页面：

1. 登录后工作台。
2. 新建项目与上传。
3. 分组与资料补全。
4. 商品创作台。
5. 生产队列与审核。

管理员页面可以保留 Django Admin 加少量自定义 dashboard，不先做复杂后台。

## 7. 后端取舍

当前后端不需要全部推倒。

可以保留：

- Django 登录和权限。
- 图片上传。
- 商品分组数据模型。
- Prompt job。
- 生图任务模型。
- 假 APIMart 模式。
- 单张重做和历史版本。
- Docker 部署。

需要改：

- 前端信息架构。
- 页面命名。
- Snapshot 的展示方式。
- 预检结果展示。
- Prompt 优化结果结构。
- 输出槽位模板。
- 审核/导出页面。

产品体验和交互复杂度已超过 Django 模板加原生 JavaScript 的合适边界。已确认采用 React + TypeScript + Vite 构建运营工作台；Django 继续负责 API、鉴权、任务和后台。详细迁移边界见 `../superpowers/specs/2026-07-29-react-frontend-architecture-design.md`。

## 8. 明天可落地版本的验收标准

如果目标是“明天看到像样且能直接用的项目”，重新定义为：

- 能登录。
- 首页是生产控制台，不是普通列表。
- 能拖拽/选择文件夹上传。
- 上传后看到商品卡片网格。
- 每张图默认一个商品。
- 能把多张图拖到同一个商品卡。
- 能填写全局要求和商品资料。
- 能选择 Shopee/TikTok、站点、套图模板、比例。
- 能看到 AI brief 草稿和每张图计划。
- 生成前有清晰预检。
- 假模式可跑完整生产队列。
- 结果页能审核、驳回、只重做失败项。
- 页面没有 raw JSON。
- 所有关键状态对运营可读。

真实付费生图和 OSS 正式密钥仍需轮换、配置和授权后再开。

## 9. 决策建议

推荐路线：

1. 先按“批量生产型商品图平台”做，不做自由画布工具。
2. 创作台只做商品图必要控制：参考图、套图槽位、风格、brief、版本、审核。
3. Prompt 由 AI 生成，用户编辑的是结构化 brief。
4. Shopee/TikTok 规则做成模板和 checklist。
5. 后端沿用当前 MVP 的可靠任务模型，主要重做前端和页面流程。

不推荐路线：

- 继续在旧批次详情页上堆按钮。
- 让用户直接写大段 prompt。
- 把实时状态展示为 JSON。
- 首版就做完整画布、图层和在线 PS。
- 在平台规则未确认前承诺自动合规。

## 10. 已确认决策与下一步

已确认：选择 A“批量生产型”为主；B“自由创作型”只保留单商品创作台必要的参考图、套图槽位、Brief、版本与审核能力。
